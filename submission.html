01Data structure and relationships

Twenty-two modules. Three decisions shape all of them.

The academic year is an entity, not a text field. Every year-scoped record points at an Academic_Years record, which is what makes history queryable instead of overwritten.

Class_Sections is the class instance for one year — Grade 5-A in 2026-27 — and it is what students actually attach to. Classes stays a year-independent grade master, so adding next year's sections never touches this year's.

Enrollments is the history spine. One row per student per academic year, holding that year's section, roll number, attendance counters and final result. Promotion never edits an old row: it closes the current Enrollment and opens a new one. Last year's class, attendance percentage and results stay intact and reportable for as long as the school keeps the org.

Junctions, not multi-selects

A relationship that carries its own data gets its own module. Subject_Allocations (section × subject × teacher × periods) is what answers "which teachers and subjects belong to this student" — through Student → Enrollment → Class_Section. Exam_Schedules (exam × section × subject × max marks) is what lets a 25-mark unit test and a 100-mark final coexist without a line of extra code — mark entry validates against that record, never against a hardcoded ceiling.

Integrity is pushed into the platform

Everything the CRM engine can enforce declaratively is enforced declaratively, because that holds against the UI, the API and imports alike — not just against my code path.

GuardMechanism
Two attendance rows for one student on one dateAttendance_Key — unique field
Two marks for one student / exam / subjectMarks_Key — unique field
A student enrolled twice in one yearEnrollment_Key — unique field
Duplicate Student ID under concurrent admissionsStudent_ID unique + token-verified counter
Marks above the paper maximumValidation rule + pre-save Client Script + server backstop
Attendance dated in the futureValidation rule

Deluge is used only where a rule has to look at other records — holidays, enrolment status, installment balances, class rank.

Derived numbers are stored, not recomputed

Attendance percentage, fee outstanding, exam totals and ranks are maintained incrementally by workflow functions and read as stored values. A portal that recomputes a year of attendance on every page load stops scaling somewhere past a few hundred students. Storing them also means the record, the dashboard and the parent's screen always agree — there is only one place each number is calculated.

02CRM ↔ Creator integration

CRM owns the data. Creator renders it live. Nothing is duplicated.

The parent portal is a pages-first Creator app. Every screen is a Page whose Deluge snippet calls a function that reads from CRM over COQL at render time. Creator holds three small forms — an identity cache, an access log, and the leave requests it originates. It holds no students, no marks, no attendance, no fees.

Why pull instead of a scheduled sync

The obvious build copies Students, Attendance, Marks and Fees into Creator forms on a timer. I went the other way deliberately.

Scheduled syncLive pull chosen
Copies of a given mark21
Staleness windowup to one sync intervalnone
Failure modesilent divergence portal shows a fee unpaid after the parent paidan API error — visible, retryable
Cost as the school growsO(all records), every cycle, foreverO(what a parent actually opens)
Reconciliation coderequired, and the buggiest part of the projectnone

A parent portal is low-traffic and read-heavy: a few hundred page views a day against a database of hundreds of thousands of rows. Copying the whole database every night to serve that is backwards. Pulling the ~30 rows a parent actually opens is cheaper and correct by construction — the portal cannot show a stale fee balance because it has no fee balance of its own. The trade-off is a live dependency on CRM and per-page latency; both are handled by caching only the identity resolution (30-minute TTL) and keeping every page to a single COQL call with enumerated columns.

How a parent is connected to a student

The key is the parent's email, and it is established at admission time, not by the parent. When a lead converts, CRM creates or reuses a Contact with that email and points the Student's Parent lookup at it. Creator is published as a Customer Portal, so zoho.loginuser is the same string as Contacts.Email.

No student ID, roll number or date of birth is ever used as a credential. Those are guessable, and they are printed on every report card.

The authorisation gate

Every data function begins with portal.assertStudentAccess(studentId), which re-resolves the signed-in parent and checks the requested student against their own children. A student id arriving in a URL is a hint about which child to display — never a grant of access. Denials are written to the access log. That single call is the difference between a parent portal and an IDOR.

Three channels, each scoped to what it needs

ChannelCarriesPrivilege
Creator → CRM, readCOQL, one call per page, enumerated columnsread-only scopes on a dedicated integration user
Creator → CRM, writeLeave_Requests create — the entire write surfaceexactly one scope
CRM → Creator, pushonly two events: the parent↔student mapping changed, and a leave was approved or rejectedshared-secret authenticated

Those two pushes exist because they are the only things a pull cannot discover: Creator cannot know its identity cache went stale, and a parent should not have to poll for an approval. Everything else is pulled.

Changes are handled through one code path

When the school approves a leave, CRM upserts the affected school days as Approved Leave attendance on the unique key — so approval flows through the same rollup as ordinary marking. A corrected attendance row updates in place and the rollup adjusts by delta. A bounced cheque flips the payment's status and the fee summary is re-derived from successful payments only, never incrementally patched. Every entry point is safe to run twice.

03Additional feature — early-warning engine

The problem I picked

A school already holds every signal it needs to catch a child slipping — attendance, marks, fee status. It just holds them in three modules that nobody joins.

Individually each signal is ignorable: one absence is nothing, one bad unit test is nothing, a late instalment is an accounts matter. Together they are the textbook profile of a student about to fail the year or leave. In most schools the pattern first becomes visible at the parent-teacher meeting — one to four months after an intervention would still have worked.

I chose it over bulk report-card PDFs or a transport module for two reasons. It needs no new data entry — every input is already captured for other purposes, which is why most school-software features go unused. And it converts data the school already owns into an action with a specific person's name on it, rather than another dashboard.

What it does

Alongside it runs a same-day "your child was marked absent today" alert — one query, one batched mail-out, deduplicated by a stamp on the attendance row. Thresholds, weights and band cut-offs live in an App_Settings record, so the school retunes the model without a developer.

Why it is built this way

This is the only thing in the system that touches every student every night, so it is where optimisation actually bites.

  • No N+1 queries. The naive version queries attendance, marks and fees per student — 6,000 API calls a night at 2,000 students, which exhausts the daily credit budget before it finishes. The engine instead runs a fixed number of paged COQL sweeps, 200 rows a page, and joins them in memory by student id in one pass.
  • It reads pre-aggregated values. Attendance % is already maintained on the Enrollment; exam percentages already live on Exam_Results. Nothing is re-aggregated. The only raw scan is a 14-day absence window for streak detection — bounded, not growing with the year.
  • It notifies on band change, not on state. Without that rule, 80 at-risk students means 80 identical emails every night and parents mute the sender inside a week. It is the most important line in the file.
  • Writes are batched — upsert, 100 per call, workflow triggers suppressed — so no workflow storm follows.
  • Idempotent and resumable — a unique Risk_Key means re-running updates rather than duplicates, and every loop is page-bounded so a runaway data condition cannot spin into the execution ceiling.
Per nightly run, 2,000 studentsNaiveThis engine

The scoring function is deliberately linear and transparent, so a class teacher can see exactly why a child was flagged. The next step is to backtest the weights against the school's own history — which students actually failed or left — and retune. Because the weights are already data rather than code, that is a configuration change, not a rewrite.
